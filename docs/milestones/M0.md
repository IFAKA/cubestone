# M0: Mac-First Core and Embedded-Portability Validation

## Purpose

M0 answers one question before gameplay work expands:

> Can Cubestone be developed and played on Mac now, while using one portable
> deterministic/regenerable voxel core plus bounded chunk cache to feed a
> genuine 3D DDA renderer at 240x135 and also build for ESP32-S3 N16R8 later?

M0A proves architecture and correctness without physical-hardware performance claims. M0B later measures the same architecture on physical N16R8-class hardware.

## Authority

This milestone is subordinate to `docs/constraints.md`, `docs/architecture.md`, and `docs/benchmark-contract.md`. It converts those specifications into implementation phases. It must not silently override them.

## M0A deliverable

A repository in which the same platform-independent core can:

- deterministically answer `blockAt(x,y,z)` over effectively unbounded horizontal coordinates
- answer the same queries through a candidate bounded chunk cache
- prove cached answers equal the procedural oracle
- render opaque voxel geometry using genuine 3D DDA into a 240x135 RGB565 framebuffer
- run interactively through an SDL3 desktop harness
- emit deterministic correctness/golden results and structured benchmark metrics
- build as ESP-IDF firmware for ESP32-S3 N16R8 assumptions
- boot under the Wokwi integration target and expose resource/integration diagnostics

No M0A result may claim the physical 30 FPS target has been met.

## M0A acceptance contract

M0A has staged implementation gates and one final acceptance gate. A phase is
accepted only when its exit evidence passes from a clean implementation state;
passing an earlier phase does not imply that later systems exist. The final
M0A gate requires every item in `docs/benchmark-contract.md` section 14,
including native correctness, deterministic goldens, structured benchmarks,
ESP32-S3 build/integration, and Wokwi smoke evidence. Physical performance is
explicitly excluded from M0A and remains an M0B requirement.

## Required implementation phases

The phases are ordered to keep the initial implementation small and falsifiable.
Later phases may not be pulled into an earlier phase merely because their
interfaces are already described below.

### Phase 0: Native core foundation

Create only the native CMake/test skeleton and a minimal portable-core identity
test. Do not add world, renderer, SDL, ESP-IDF, or simulator code in this
phase. Pin supported desktop dependencies/toolchain assumptions in the build
configuration, while keeping the core target usable without SDL3.

Exit evidence:

- native configure/build succeeds
- one minimal test executable runs through CTest
- `src/core` contains no platform dependency
- the build layout leaves a single source path for the future ESP-IDF core
  component; ESP-IDF integration is intentionally deferred to Phase 7

### Phase 1: Fundamental types and deterministic procedural oracle

Implement coordinate/block types and `ProceduralWorld`. Terrain may be deliberately simple but must be deterministic, include enough 3D geometry for fixed benchmark scenes, and behave correctly at negative chunk/world coordinates.

Test at minimum coordinates around `-17,-16,-15,-1,0,1,15,16,17` on relevant axes, repeated seeds, large signed coordinates, and deterministic repeated queries.

Exit evidence: all oracle/coordinate tests pass with no platform dependency in core.

### Phase 2: Procedural DDA and framebuffer vertical slice

Implement ray traversal against the block-source boundary. M0 supports opaque solid/air behavior and flat material output only.

Required edge cases include axis-aligned rays, negative directions, diagonal rays, starts on voxel boundaries, starts inside solids, near-zero direction components, maximum-distance termination, and vertical/world-height behavior defined by the oracle.

Exit evidence: deterministic DDA unit tests pass and traversal exposes query/step counters.

Render exactly 240x135 RGB565 from a camera through DDA. No allocation is permitted inside `renderFrame()` or per-ray/per-step paths. Render distance/FOV/workload values used by benchmark scenes must come from the benchmark contract, not ad hoc tuning.

Exit evidence:

- deterministic fixed camera produces stable framebuffer hash/golden result
- allocation instrumentation proves zero render-path allocations after initialization
- rays, DDA steps and world-query counts are reported

### Phase 3: Candidate chunk representation and bounded cache

Implement the first experimental 16x16x64 logical chunk representation
described by the architecture. The procedural source remains the correctness
oracle. Cache capacity/ownership must be explicit and bounded. Do not assume
the <=8 KiB average hypothesis is true.

Measure actual encoded bytes for fixed representative generated chunks. Report
distributions, not a fabricated average.

Exit evidence:

- encode/decode/lookup tests pass
- randomized and boundary query sets satisfy `cached.blockAt(p) == procedural.blockAt(p)`
- cache hit/miss and resident-byte counters exist
- no correctness depends on cache residency
- procedural and cached render outputs remain equivalent for the fixed scene

### Phase 4: SDL3 desktop harness

Add input/presentation only. SDL3 must not enter `src/core`. Preserve 240x135 internal rendering regardless of display-window scale. Provide first-person camera movement/look sufficient to inspect the world.

Exit evidence: desktop executable is playable and presentation/input changes do not alter deterministic headless goldens.

### Phase 5: Fixed benchmark suite

Implement the fixed S0 FLAT, S1 SURFACE, S2 CAVE and S3 CACHE-STRESS workloads defined by `docs/benchmark-contract.md`. Results must be machine-readable and include workload/build/platform identity.

Native timing is useful for regression/algorithm comparison only. It is not ESP32 performance evidence.

Exit evidence: repeated runs preserve workload identity and structured result schema; benchmark correctness counters are plausible and tests remain green.

### Phase 6: ESP32-S3 integration and memory accounting

Build the shared core under the pinned ESP-IDF target/configuration. Implement explicit platform allocation classes and capability-aware resource counters as specified. Keep display/DMA policy behind the platform boundary. Do not infer a final DMA/framebuffer strategy before physical measurement.

Exit evidence:

- `idf.py build` succeeds for esp32s3
- binary fits configured flash layout
- configured PSRAM assumptions are visible/validated at runtime where simulation permits
- internal/PSRAM free/minimum/largest-block diagnostics are emitted
- core contains no ESP-IDF/FreeRTOS includes

### Phase 7: Wokwi integration

Boot the real ESP-IDF firmware with the repository's Wokwi configuration. Use Wokwi only for functional integration, memory configuration, assertions, watchdog/task behavior, and deterministic output.

Never use Wokwi timing as FPS, throughput, memory-bandwidth, DMA, or PSRAM-contention evidence.

Exit evidence: firmware boots without assertion/watchdog failure and expected integration diagnostics appear.

### Phase 8: M0A audit

Run every required build, test, golden and benchmark command from a clean state. Compare every M0A criterion in `docs/benchmark-contract.md` against evidence. Record failures instead of weakening gates.

Exit evidence: every non-physical M0A criterion passes, or M0A remains explicitly incomplete with blockers in `STATE.md`.

## Hard non-goals

M0 must not add mobs/entities, inventory/items, crafting, textures, propagated lighting, sky/day-night, weather, fluids, redstone, structures/villages, persistence/microSD, sound, networking/multiplayer, menus/UI, farming, furnaces, brewing, enchanting, full biome simulation, or an adaptive performance controller.

Do not add speculative abstractions for these systems.

## Evidence rules

Facts from source/tests/build output may be recorded as facts. Desktop measurements are desktop measurements. Wokwi measurements are simulator measurements. Resource budgets explicitly marked as hypotheses remain hypotheses. Physical ESP32-S3 performance is unknown until M0B.

Any optimization of a measured hot path requires same-workload before/after evidence. Correctness and workload must remain unchanged. A faster result obtained by silently reducing rays, distance, geometry, resolution, or work is invalid.

## Stop/escalate conditions

Stop the affected implementation and record the blocker when:

- hardware/ESP-IDF documentation contradicts an authoritative project constraint
- two authoritative project documents conflict materially
- satisfying a task would require violating a hard constraint
- a required dependency/toolchain cannot support the specified target
- a proposed architecture change is required to proceed
- deterministic oracle and cached results cannot be reconciled without changing the specified model
- tests reveal that a previously recorded architectural assumption is false

Do not solve these by silently changing requirements.

## M0A definition of done

M0A is done only when the benchmark contract says it is done. In particular, completion requires the portable core, procedural/cache oracle, true 3D DDA, RGB565 renderer, SDL3 harness, deterministic tests/goldens, structured benchmarks, ESP32-S3 build, Wokwi integration, and resource instrumentation to pass their specified gates.

`>=30 FPS P95`, real PSRAM/cache contention, display/DMA throughput, and real cycle performance remain M0B physical-hardware questions.
